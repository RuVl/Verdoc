# Остаток считается запросом, а не хранится в колонке

`Passport.quantity` был денормализованным счётчиком, который код обязан был поправлять при каждом
резерве, продаже и возврате, плюс сигнал в `passport/signals.py` на создание и удаление файлов.
Механизм уже разъезжался — команда `passport/management/commands/resync_quantity.py` существовала
ровно для того, чтобы пересчитать колонку заново. Расхождение видно покупателю: витрина показывает
«в наличии», а `reserve()` падает при оплате, или наоборот — товар скрыт, хотя файлы есть.

Колонку удаляем. «В наличии» выводится из тех же строк, которые и есть правда:
`StockItem` без активной `Allocation` (см. [ADR-0001](./0001-allocation-as-single-source-of-truth.md)).
Вместе с колонкой удаляются `passport/signals.py` и `resync_quantity`.

```sql
SELECT p.id, COUNT(s.id) AS available
FROM catalog_product p
LEFT JOIN catalog_stockitem s ON s.product_id = p.id
WHERE NOT EXISTS (
    SELECT 1 FROM sales_allocation a
    WHERE a.stock_item_id = s.id AND a.state <> 'RELEASED'
)
GROUP BY p.id;
```

## Consequences

- Рассинхрон невозможен по построению: числа нет, есть только выведение.
- Витрина выполняет этот `COUNT` на каждой загрузке. При десятках товаров и сотнях единиц —
  доли миллисекунды.

## Когда возвращать кэш

Порог — примерно десятки тысяч товаров в каталоге либо заметная доля времени ответа витрины
на этом запросе. Рецепт возврата, чтобы не изобретать заново:

1. `AddField(Product.available_cache, PositiveIntegerField(default=0, editable=False))`.
2. `RunPython` заполняет его запросом выше.
3. Пересчёт по сигналам `post_save`/`post_delete` на `Allocation` и `StockItem` — оба, иначе
   загрузка новых файлов не увеличит остаток.
4. Команда сверки по крону, сравнивающая кэш с запросом, — обязательна. Именно её отсутствие
   и делало старую схему хрупкой.

Важно: возвращать кэш как **отдельное поле рядом с выведением**, а не вместо него. Тогда сверка
имеет с чем сравнивать.
