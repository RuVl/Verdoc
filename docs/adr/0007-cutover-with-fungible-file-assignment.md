# Выкатка в окне простоя, с раздачей взаимозаменяемых файлов при переливе

Ранняя версия плана миграции (`docs/db-refactoring/data-migration-plan.md`) фиксировала как
известное ограничение: для `PENDING`-заказов невозможно восстановить, какой файл чей, поэтому
миграцию надо делать при нуле активных заказов.

Это неверно. Единицы одного товара **полностью взаимозаменяемы** — в этом суть модели.
Значит `RESERVED`-файлы товара можно раздать позициям `PENDING`-заказов того же товара
в произвольном порядке: покупатель получит файл того товара, за который платит.
Неоднозначность есть только между двумя конкурирующими заказами, и она безвредна ровно потому,
что файлы одинаковы.

То же для `SOLD`-файлов без `DownloadLink` (те самые «ошибки при продаже» из `HasSoldErrorFilter`):
они раздаются позициям, у которых не хватает аллокаций. Текущий баг чинится прямо в миграции.

Требование «ноль `PENDING`» снимается, поэтому выкатка — короткое окно простоя ночью,
без предварительного принудительного `expire`.

## Considered Options

- **Dual-write без простоя** (три релиза: пишем в обе схемы, переключаем чтение, удаляем старую).
  Ноль простоя, но код периода dual-write — самая багоопасная часть всей работы: каждый переход
  состояния пишется дважды в две разные модели согласованно. При ночном трафике близком к нулю
  цена не оправдана.
- **Окно простоя с предварительным `expire_transactions`.** Проще скрипт перелива (только `SOLD`),
  но убивает живые неоплаченные заказы: покупатель, оплативший через минуту после окна, попадает
  ровно в сценарий позднего платежа из инцидента 652.

## Consequences

- Порядок: дамп → заглушка nginx → `migrate` + перелив → SQL-сверки → снять заглушку.
  Старые таблицы дропаются следующим релизом, а не в этом же окне.
- Откат — восстановление дампа и старый образ (см. [ADR-0003](./0003-new-apps-instead-of-rename.md)).
- Перед выкаткой надо убедиться, что Plisio ретраит callback при 5xx: в окно простоя он получит
  ошибку.
- Старый URL `/api/order/file/<email>/<uuid>/` остаётся рабочим — `uuid` переезжает
  в `Allocation.token` один-в-один. Иначе все ранее разосланные письма умрут в момент выкатки.
