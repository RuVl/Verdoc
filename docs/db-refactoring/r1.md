# R1 — схема, перелив, бэкенд

Ветка `feature/db-refactoring-r1`. Цель: перевести данные и бэкенд на целевую схему
([`target-schema.md`](./target-schema.md)), **не меняя ничего для покупателя**. Письмо прежнего
вида, фронт не трогаем. Смысл в том, чтобы ошибки миграции ловились без шума от нового интерфейса.

Контракт API, который обязан остаться байт-в-байт (проверено по `frontend/src`):

| Endpoint | Форма |
|---|---|
| `GET /api/countries/` | `[{id, code, name_en, name_ru, passports: [{id, name_en, name_ru, quantity, price, price_currency}]}]` |
| `POST /api/order/` | `{user_email, items: [{passport_id, quantity}]}` → `{redirect_url}` |
| `POST /api/send-links/` | `{email}` → 200 |
| `GET /api/order/file/<email>/<uuid>/` | поток файла |
| `POST /api/order/status` | callback Plisio |

Ключи `passports`, `quantity`, `passport_id`, `user_email` сохраняются как **имена в API**, хотя
модели называются иначе. Это осознанный слой совместимости на R1, снимается в R2 вместе с фронтом.

## 1. Документы

Разбить `rollout.md` на `r1.md` / `r2.md` / `r3.md`, по одному на релиз, с чеклистами.

## 2. catalog

`backend/catalog/`: `models.py`, `translation.py`, `admin.py`, `forms.py`, `serializers.py`,
`views.py`, `urls.py`, `apps.py`, `management/commands/seed_testdata.py`.

- `Country` — копия текущей, включая `code2flag` и `flag`.
- `Product` — `name` (translated), `price`, `country` FK `related_name="products"`.
  **Без `quantity`.**
- `StockItem` — `file`, `product` FK `related_name="stock_items"` (`SET_NULL`). **Без `status`.**
- `StockItemQuerySet.available()` — `~Exists(активная Allocation)`.
- `ProductQuerySet.with_available()` — `Subquery(Count)` по свободным единицам, `Coalesce(..., 0)`.
- Сериализаторы отдают `quantity` из `available` и `passports` из `products` — слой совместимости.
- `seed_testdata` переносится сюда, без `quantity` (счётчика больше нет).
- Сигналов нет.

## 3. customer

`backend/customer/`: `models.py`, `admin.py`, `apps.py`.

- `Customer` — `email` unique, `access_token`, `access_token_expires_at`, `is_subscribed`,
  `unsubscribed_at`, `created_at`.
- `rotate_access_token()` — новый токен и сброс TTL. На R1 вызывается при отправке письма,
  но ссылка на страницу покупок ещё не используется.

## 4. sales

`backend/sales/`: `models.py`, `serializers.py`, `views.py`, `urls.py`, `utils.py`, `admin.py`,
`apps.py`, `management/commands/expire_transactions.py`.

Переходы состояний живут на моделях, как и сейчас, но владелец состояния — `Allocation`:

| Метод | Что делает |
|---|---|
| `OrderItem._allocate(count)` | берёт свободные единицы, создаёт `RESERVED`-аллокации |
| `OrderItem.reserve()` | `_allocate(quantity)` с защитой от повторного резерва |
| `OrderItem.deliver()` | `RESERVED` → `DELIVERED`, выдаёт токены; доаллоцирует при позднем платеже |
| `OrderItem.release()` | `RESERVED` → `RELEASED`, идемпотентно |
| `Order.mark_paid()` | ставит `paid_at` один раз, возвращает `True` при первом вызове |
| `Order.deliver()` / `Order.release()` | по всем позициям |

- `Allocation.Meta.constraints`: `UniqueConstraint(fields=["stock_item"],
  condition=~Q(state="RELEASED"), name="one_active_allocation_per_stock_item")`.
- `Transaction` — FK на заказ, `txn_id` unique, плюс `pending_amount` и `tx_urls`.
- `PaymentCallbackLog` — пишется **до** атомарного блока, чтобы пережить откат.
- `expire_transactions` — то же имя команды, чтобы `backend/cronjob` не менялся.

## 5. Перелив данных

`sales/migrations/0002_transfer_from_legacy.py`, одна `RunPython`, атомарно. Порядок и SQL-сверки —
[`data-migration-plan.md`](./data-migration-plan.md).

**PK сохраняются обязательно.** `order_number` в инвойсах Plisio — это `Order.id`, и по уже
выставленным инвойсам придут callback'и со старыми номерами. После перелива сбрасываются
последовательности (`setval`).

Аллокации восстанавливаются в порядке: точные связи из `DownloadLink` → раздача взаимозаменяемых
`SOLD` → раздача взаимозаменяемых `RESERVED` ([ADR-0007](../adr/0007-cutover-with-fungible-file-assignment.md)).

Историческая цена не существует — снапшоты старых позиций заполняются текущей ценой каталога,
инвариант `sum(unit_price_usd × qty) == total_price` включается только для заказов после выкатки.

Миграция **не требует** установленных `passport`/`order`: зависимость от их миграций добавляется в
список только пока приложения в `INSTALLED_APPS`, а каждая функция перелива молча выходит, если
исторические модели не находятся. После релиза, который удаляет legacy-приложения, `0002` остаётся
применимой и на чистой БД просто ничего не делает — её не нужно ни править, ни схлопывать.

## 6. API на новой схеме

- `backend/urls.py` подключает `catalog.urls` и `sales.urls`.
- `PlisioCallbackView`: `update_or_create` по `txn_id` (не по заказу), `PaymentCallbackLog`,
  `mark_paid()`, письмо только при первом переходе в PAID — дубликат callback'а больше не шлёт
  второе письмо и не отдаёт 409.
- `SendDownloadLinksView`: `order.deliver()` (идемпотентен и сам добирает недостающее из стока)
  → обновление токенов → письмо. Костыль `get_order_item_links()`, вслепую цеплявший чужие
  `SOLD`-файлы, не переносится: аллокации теперь точные.
- `DownloadLinksView`: поиск `Allocation` по `token`, проверка почты сохраняется.
- Письмо: прежний текст, N ссылок, собранных из `Allocation.token`.

## 7. Старые приложения

`passport` и `order` сводятся к моделям и миграциям. Удаляются: `views`, `urls`, `serializers`,
`admin`, `signals`, `forms`, все management-команды, включая `resync_quantity` и
`repair_paid_orders`.

`passport/translation.py` **остаётся** — иначе modeltranslation захочет удалить колонки
`name_en`/`name_ru` отдельной миграцией. Уйдёт вместе с приложением в релизе-дропе.

## Проверка перед PR

```bash
make lint
make dev-test                                      # 50 тестов: catalog, customer, sales
make dev-infra && make dev-migrate                 # миграции встают на пустой БД
make dev-manage c="seed_testdata --flush"
make dev-manage c="update-rates"                   # или make update-rates
make dev-backend                                   # + make dev-frontend
```

Тесты закрывают то, что раньше ловилось только на проде: резерв и повторный резерв, выдача и её
идемпотентность, поздний платёж (оба исхода), дубль callback'а, смена валюты, TTL токенов,
доаллокация недовыданной позиции, производный остаток и партиальный уникальный индекс.

Совместимость API проверена не на глаз: старый и новый `CountrySerializer` отрендерены на одной и
той же БД, JSON совпал байт-в-байт.

Ручной сценарий: витрина показывает остатки → заказ → инвойс Plisio → callback → письмо →
скачивание по ссылке → форма «мои покупки» → повторное письмо.

Проверка перелива на копии прод-дампа — отдельно, по
[`data-migration-plan.md`](./data-migration-plan.md), до выкатки.

## Выкатка

1. Убедиться, что Plisio ретраит callback при 5xx.
2. Прогон на копии прод-дампа: `make db-dump` → `make db-restore` → `make dev-migrate` → сверки.
3. `make db-dump DUMP=backups/pre-refactor.sql` на проде.
4. Заглушка nginx.
5. `make migrate`.
6. SQL-сверки. Любое расхождение, кроме остатков, — стоп и откат на дамп.
7. Снять заглушку.
8. Дымовой тест: заказ, оплата, письмо, скачивание, ссылка из старого письма.

Дроп `passport` и `order` — **отдельным PR** после полного цикла заказа на проде.
