Зависит от R1 (`Customer`, `paid_at`, снапшоты, `Transaction` как FK). От R2 не зависит,
но письмо рассылки логично вести на страницу покупок, поэтому порядок такой.

## 1. Рассылки на новой схеме

Ветка `feature/add-broadcasting` уже содержит `Broadcast`, TinyMCE-редактор в админке,
команду `broadcast` и страницу отписки. Переносится с двумя изменениями:

- `Unsubscribe` **не переносится** — отписка это `Customer.is_subscribed` + `unsubscribed_at`.
  Если ветка успела попасть на прод, строки `Unsubscribe` переливаются в `Customer` миграцией
  R1 (см. [`data-migration-plan.md`](./data-migration-plan.md), шаг 2). Терять отписки нельзя:
  это репутация домена у почтовых провайдеров.
- `get_broadcast_recipients()` из `mailing/services.py` — вместо `distinct()` по строкам
  `Order.user_email` с `exclude(email__in=unsubscribed)` становится обычным queryset:

  ```python
  Customer.objects.filter(is_subscribed=True, orders__status__in=PAID_STATUSES).distinct()
  ```

- Токен отписки (`django.core.signing`, соль `broadcast-unsubscribe`) остаётся как есть —
  он не завязан на схему.

## 2. BroadcastDelivery

Строка на пару `(broadcast, customer)` с `UNIQUE`. Даёт три вещи, которых нет у счётчиков:

- повтор **только** упавшим;
- идемпотентность — крон упал посередине, повторный запуск не шлёт дубли;
- ответ на вопрос «получал ли этот покупатель рассылку X».

Счётчики `total_recipients` / `sent_count` / `failed_count` / `error_log` на `Broadcast`
становятся производными от `BroadcastDelivery` (свойства или аннотации), поля удаляются.

Команда `broadcast` работает так: создать `PENDING`-строки на всех получателей, затем идти по
`PENDING` и переводить в `SENT`/`FAILED`. Падение на середине не теряет прогресс.

## 3. Статистика

Предагрегатов нет — при текущем объёме `TruncDay` + `Sum` по `OrderItem` считается мгновенно.
Материализованные таблицы имеет смысл заводить где-то от сотен тысяч позиций, до этого они
только источник рассинхрона.

Данные, которые для этого появились в R1:

| Метрика | Источник |
|---|---|
| выручка по дням | `Order.paid_at` + `OrderItem.unit_price_usd` |
| продажи по товарам и странам | `OrderItem.product_name` / `product_id` → `country` |
| конверсия | `Order.status` по когортам `created_at` |
| реальная комиссия Plisio | `Transaction.commission` по всем инвойсам заказа |
| недоплаты | `Transaction.pending_amount` |
| повторные покупатели, LTV | `Order.customer_id` |
| оборачиваемость стока | `Allocation.reserved_at` → `delivered_at` |
| результативность рассылок | `BroadcastDelivery` |

Рендер — отдельная страница в админке (`AdminSite.get_urls`) с вендоренным JS-графиком,
без CDN. Решение обратимое, ADR не нужен.

Цифры за период **до** выкатки R1 приблизительны: `paid_at` восстановлен из
`Transaction.updated_at`, а снапшоты цен заполнены текущей ценой каталога. Это надо подписать
на самом графике, а не только в документации, иначе через год кто-то будет объяснять аномалию
сезонностью.
